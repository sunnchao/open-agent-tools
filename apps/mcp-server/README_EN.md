# MCP Gateway

[中文](./README.md) | [Platform overview](../../README_EN.md)

`@open-agent-tools/mcp-server` is the data-plane entry point for the MCP platform. It loads published service snapshots from PostgreSQL, validates MCP Client API Keys and Grants, and exposes Tools and Prompts over stateless Streamable HTTP.

## Request flow

1. An MCP Client sends a `POST` request with a Bearer API Key to `/mcp/services/:serviceSlug`.
2. The Gateway parses the Key ID and verifies the secret against its scrypt hash.
3. It validates the Key, Client, expiry, service state, current published version, and Grant.
4. It creates a request-scoped `McpServer` containing only authorized capabilities.
5. `tools/list` and `prompts/list` return metadata from one published version snapshot.
6. `prompts/get` validates arguments and renders the template inside the Gateway.
7. `tools/call` validates the JSON Schema and submits a digest-pinned execution job to BullMQ.

The Gateway never loads Tool modules, installs dependencies, or starts Docker containers directly.

## Supported MCP capabilities

- `tools/list`
- `tools/call`
- `prompts/list`
- `prompts/get`

Managed services currently do not support `resources/list` or `resources/read`.

## Endpoints

```text
POST   /mcp/services/:serviceSlug
GET    /health
```

The MCP endpoint uses stateless Streamable HTTP. `GET` or `DELETE` on the service path returns an MCP-compatible `405 Method Not Allowed`.

Example headers:

```http
POST /mcp/services/reporting HTTP/1.1
Host: localhost:4100
Authorization: Bearer mcp.<key-id>.<secret>
Content-Type: application/json
```

The request body is generated by an MCP SDK Streamable HTTP Client.

## Authentication and authorization

Authentication prerequisites:

- The API Key exists, is `ACTIVE`, is unexpired, and matches its hash.
- The owning Client is `ACTIVE`.
- The service is `ACTIVE` and its current version is `PUBLISHED`.
- A service Grant exists and includes `mcp:connect`.

Operation scopes:

| MCP operation  | Scope          |
| -------------- | -------------- |
| `tools/list`   | `tools:list`   |
| `tools/call`   | `tools:call`   |
| `prompts/list` | `prompts:list` |
| `prompts/get`  | `prompts:get`  |

`toolNames` and `promptNames` filters affect both listing and invocation/get operations. Unauthorized names are treated as not found so hidden capabilities are not disclosed.

For example, for a service containing Tools `A`, `B`, and `C`:

| MCP Client Token | Grant `toolNames` | Visible through `tools/list` | Allowed through `tools/call` |
| ---------------- | ----------------- | ---------------------------- | ---------------------------- |
| token1           | `["A", "B"]`      | A and B                      | A and B only                 |
| token2           | `["C"]`           | C                            | C only                       |

Both Grants must include `mcp:connect`, `tools:list`, and `tools:call`. A token1 call to C or a token2 call to A/B returns Tool not found and creates no execution job.

## Environment variables

```bash
cp .env.example .env.local
```

| Variable        | Required                | Description                                            |
| --------------- | ----------------------- | ------------------------------------------------------ |
| `DATABASE_URL`  | Yes                     | Same MCP management database used by the Control Plane |
| `REDIS_URL`     | Required for Tool calls | BullMQ Tool execution queue                            |
| `MCP_HTTP_PORT` | No                      | HTTP port, default `4100`                              |

Without `REDIS_URL`, the Gateway can serve Prompt paths, but `tools/call` cannot complete for services containing Tools.

## Running

```bash
pnpm --filter @open-agent-tools/mcp-server dev
```

Production build and start:

```bash
pnpm --filter @open-agent-tools/mcp-server build
pnpm --filter @open-agent-tools/mcp-server start
```

The build script copies `src/resources` to `dist/resources`. This directory belongs to the original static-resource demo and does not represent managed MCP Resources support.

## Data sources

`PostgresGatewayRepository` reads these management tables:

- `api_keys`
- `api_clients`
- `client_grants`
- `mcp_services`
- `mcp_service_versions`
- `mcp_tools`
- `mcp_prompts`

The Control Plane, Gateway, and Worker must use the same PostgreSQL database. The Gateway only accepts the `PUBLISHED` version referenced by the current service.

## Tool calls

- Tool arguments are validated with Ajv 2020.
- Invalid arguments do not create execution jobs.
- Jobs are written to the `mcp-tool-execution` queue.
- Each job pins the service ID, version ID, image digest, Tool name, arguments, Client ID, deadline, and limits.
- BullMQ Tool jobs are not automatically retried, preventing duplicate side effects for non-idempotent Tools.
- Worker results are validated again against the shared MCP result contract.

## Prompt rendering

- Prompt definitions come from the published version.
- `prompts:get` scope is required.
- Only declared string arguments are accepted.
- Missing required arguments and undeclared arguments return protocol-safe errors.
- Rendering uses the same `renderPrompt` function from `@open-agent-tools/mcp-contracts` as admin preview.
- Prompts never enter the execution queue or start Tool containers.

## HTTP errors

| Scenario                                             | Status |
| ---------------------------------------------------- | ------ |
| Missing, malformed, unknown, revoked, or expired Key | `401`  |
| Missing service Grant or `mcp:connect`               | `403`  |
| Service does not exist                               | `404`  |
| Service is inactive or has no published version      | `503`  |
| Unsupported method                                   | `405`  |
| Unhandled internal error                             | `500`  |

MCP method errors are returned by the SDK as safe JSON-RPC/MCP errors without internal stacks or host paths.

The test drops and recreates the target database's `public` schema and must use a dedicated test database.

## Current limitations

- Only managed MCP services are supported; remote MCP forwarding is not wired in.
- Each request creates a stateless MCP Server; long-lived sessions are not provided.
- Distributed authorization/capability caching and active invalidation are not integrated yet.
- Production rate limits, concurrency quotas, and complete observability must be supplied by the gateway infrastructure.
